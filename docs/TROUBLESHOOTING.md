# Повторный запуск ChatGPT и ошибка Windows sandbox

## Две независимые записи автозапуска

У `OpenAI.Codex` и старого `OpenAI.ChatGPT-Desktop` отдельные StartupTask. Отключение первой записи не отключает вторую. Старый пакет может оставаться зарегистрированным и показываться как ChatGPT даже без доступного InstallLocation.

При выборе Codex Desktop установщик резервирует и отключает также существующую запись `OpenAI.ChatGPT-Desktop_2p2nqsd0c76g0\ChatGPT`. При удалении восстанавливается её исходное состояние, если пользователь не изменил его позднее. Отсутствующая старая запись не создаётся; установка только Claude её не меняет. Общий параметр Windows RestartApps остаётся без изменений.

После следующего входа в Windows нужно проверить результат. Если приложение снова восстановится, собрать свежий источник запуска: отключение StartupTask само по себе не исключает восстановление Windows или сторонний launcher.

## Уведомление открывает второе окно

Отдельно подтверждён запуск из уведомления Windows: `ChatGPT.exe type=action&action=1&tag=...`, родитель svchost.exe. Пользователь подтвердил нажатие уведомления. Этот путь может создать второе окно без параметров VPN-ярлыка, даже когда первое окно запущено правильно. В наблюдавшемся втором процессе установленных TCP-соединений не было.

Отключение StartupTask не перехватывает активацию уведомлений. Существующие сетевые ограничения исполняемого файла сохраняются, однако перенаправление такой активации в защищённый launcher ещё не реализовано. До исправления открывать приложение через VPN-ярлык и возвращаться к уже открытому защищённому окну через панель задач. Окно обработки уведомления не считать подтверждением правильной конфигурации.

## Windows setup didn't finish / Setup stopped

Этот диалог не устанавливает причину. Проверить `%USERPROFILE%\.codex\.sandbox\setup_error.json` и свежий журнал того же каталога. В обнаруженном локальном случае код был `helper_sandbox_lock_failed`: NtCreateFile не мог открыть `.sandbox-bin` из-за отказа в доступе. Настройка сетевых фильтров до этого этапа проходила успешно.

Владелец, SYSTEM и администраторы имели Modify, но не FullControl на самом служебном каталоге. Добавление им FullControl только для этого каталога устранило ошибку: последующая обычная sandbox-команда выполнилась, `setup_error.json` исчез, `setup_marker.json` был заполнен. Причина появления прежнего ACL не установлена.

Для такого же подтверждённого кода ошибки выполнить из исходников в обычном 64-битном Windows PowerShell 5.1:

```powershell
.\repair-codex-sandbox.ps1
```

Скрипт проверяет владельца и отсутствие reparse points, сохраняет исходный SDDL в приватный каталог Diagnostics и меняет DACL только `.sandbox-bin`, без рекурсии. Права sandbox-пользователей, ACL дочерних файлов, сетевые правила и режим изоляции не расширяются. Затем повторить настройку sandbox в приложении и проверить обычную sandbox-команду. Без соответствующего журнала ошибки скрипт отказывает; универсальным ремонтом всех ошибок setup он не является.

На рабочем компьютере отдельно подтверждено: автозапуск обоих пакетов отключён, RestartApps остаётся включённым. Полный результат после очередной перезагрузки ещё требует проверки.

Официальная документация: [Windows sandbox и диагностика прав](https://learn.chatgpt.com/docs/windows/windows-sandbox).
