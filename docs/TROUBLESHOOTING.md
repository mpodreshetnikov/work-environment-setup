# Повторный запуск ChatGPT и ошибка Windows sandbox

## Две независимые записи автозапуска

У `OpenAI.Codex` и старого `OpenAI.ChatGPT-Desktop` отдельные StartupTask. Отключение первой записи не отключает вторую. Старый пакет может оставаться зарегистрированным и показываться как ChatGPT даже без доступного InstallLocation.

При выборе Codex Desktop установщик резервирует и отключает также существующую запись `OpenAI.ChatGPT-Desktop_2p2nqsd0c76g0\ChatGPT`. При удалении восстанавливается её исходное состояние, если пользователь не изменил его позднее. Отсутствующая старая запись не создаётся; установка только Claude её не меняет. Общий параметр Windows RestartApps остаётся без изменений.

После следующего входа в Windows нужно проверить результат. Если приложение снова восстановится, собрать свежий источник запуска: отключение StartupTask само по себе не исключает восстановление Windows или сторонний launcher.

## Уведомление открывает второе окно

Отдельно подтверждён запуск из уведомления Windows: `ChatGPT.exe type=action&action=1&tag=...`, родитель svchost.exe. Пользователь подтвердил нажатие уведомления. Этот путь может создать второе окно без параметров VPN-ярлыка, даже когда первое окно запущено правильно. В наблюдавшемся втором процессе установленных TCP-соединений не было.

Отключение StartupTask не перехватывает активацию уведомлений. Теперь установщик создаёт отдельный COM-обработчик с собственным CLSID и направляет в него ToastActivatorCLSID исходного ярлыка и CustomActivator известных AppUserModelID Codex. Исходный EXE не изменяется. При установке очищаются старые уведомления Codex, чтобы убрать записи с прежним маршрутом активации; сами чаты сохраняются.

Обработчик проверяет идентификатор приложения и формат параметров, выполняет проверку VPN, затем запускает зарегистрированный alias с закреплённым прокси, `NODE_USE_ENV_PROXY=1` и выбранным режимом GPU. Строка активации передаётся как данные, без cmd.exe. Неизвестные форматы отклоняются. Окружение стандартных модулей Windows PowerShell задаётся явно: COM-запуск не должен зависеть от PSModulePath интерактивного терминала.

На рабочем компьютере пользователь нажал настоящее тестовое уведомление: активировалось текущее окно, второго окна и ошибки не было; событие записал новый обработчик. Изолированный тест проверил холодную COM-активацию, точную передачу параметров, отказ при неизвестном AppUserModelID и лишних аргументах, восстановление исходных байтов ярлыка и повторное удаление регистрации.

Регистрация собственного CLSID выполняется в HKLM через UAC, с отдельным случайным идентификатором этой установки; настройки маршрутизации уведомлений остаются в HKCU. Исполняемый файл и конфигурация доступны только владельцу, SYSTEM и администраторам. Helper не добавляется в автозапуск, запускается по активации и завершает работу после ограниченного времени ожидания. Для этого компьютера холодный старт из одной HKCU-регистрации не прошёл тест, поэтому он не используется установщиком.

`verify.ps1` проверяет регистрацию, исходный ярлык и хеши файлов обработчика; rollback/uninstall восстанавливают только принадлежащие установке изменения, сохраняя последующие правки пользователя. Обновление приложения, изменившее его ярлык или регистрацию, требует проверки и при необходимости repair. Прямой запуск EXE и штатная активация MSIX остаются отдельными незавершёнными сценариями.

Внутри COM-callback проверяются машинная регистрация уже выбранного обработчика, исходный ярлык и приватные файлы. Проверка всех пользовательских маршрутов выполняется отдельно через `verify.ps1`: наблюдавшийся COM-процесс видел другую пользовательскую registry view, несмотря на тот же SID, поэтому её отсутствие нельзя интерпретировать как изменение настроек. Реальная проверка VPN остаётся обязательной в обоих случаях.

Для существующего старого прототипа отдельно, из повышенного Windows PowerShell 5.1:

```powershell
.\enable-codex-notifications.ps1 -LegacyGuardRoot "$env:LOCALAPPDATA\ClaudeVpnGuard"
```

Обычный переносимый установщик включает обработчик автоматически при выборе Codex Desktop. Перед установкой Codex должен быть хотя бы раз открыт, чтобы существовал его исходный ярлык уведомлений, затем полностью закрыт.

## Windows setup didn't finish / Setup stopped

Этот диалог не устанавливает причину. Проверить `%USERPROFILE%\.codex\.sandbox\setup_error.json` и свежий журнал того же каталога. В обнаруженном локальном случае код был `helper_sandbox_lock_failed`: NtCreateFile не мог открыть `.sandbox-bin` из-за отказа в доступе. Настройка сетевых фильтров до этого этапа проходила успешно.

Владелец, SYSTEM и администраторы имели Modify, но не FullControl на самом служебном каталоге. Добавление им FullControl только для этого каталога устранило ошибку: последующая обычная sandbox-команда выполнилась, `setup_error.json` исчез, `setup_marker.json` был заполнен. Причина появления прежнего ACL не установлена.

Для такого же подтверждённого кода ошибки выполнить из исходников в обычном 64-битном Windows PowerShell 5.1:

```powershell
.\repair-codex-sandbox.ps1
```

Скрипт проверяет владельца и отсутствие reparse points, сохраняет исходный SDDL в приватный каталог Diagnostics и меняет DACL только `.sandbox-bin`, без рекурсии. Права sandbox-пользователей, ACL дочерних файлов, сетевые правила и режим изоляции не расширяются. Затем повторить настройку sandbox в приложении и проверить обычную sandbox-команду. Без соответствующего журнала ошибки скрипт отказывает; универсальным ремонтом всех ошибок setup он не является.

На рабочем компьютере отдельно подтверждено: автозапуск обоих пакетов отключён, RestartApps остаётся включённым. Полный результат после очередной перезагрузки ещё требует проверки.

Официальная документация: [Windows sandbox и диагностика прав](https://learn.chatgpt.com/docs/windows/windows-sandbox).
